# 拍掌节奏游戏开发计划

更新日期：2026 年 10 月 17 日。范围：集成音乐播放、手套拍掌输入、时间校准、节奏判定、拍掌音效和音游 UI，并保留与 TouchDesigner 音乐可视化同屏的路径。当前已完成第 1 阶段的软件链路；手套接入与硬件延迟测量尚未开始。

规则依据：[拍掌节奏游戏规则与画面参考](rhythm-game-rules.md)。下文是建议顺序，技术栈与参数均不因本计划而自动确定。

## 当前实现与后续差距

根目录 `beatgame.py` 作为软件应用入口；`rhythm_game/` 包含配置、音频、计时判定、控制器和 Arcade 窗口。早期上游判定实验（提交 `5be3250`）保留在 `experiments/interval_judge.py`。

当前使用固定 90 BPM、4 秒首拍、4/4 拍的实际音乐；独立配置提供全局拍点偏移与输入补偿。音乐及预载拍手声共用 sounddevice 输出流，用 DAC 输出时间锚点映射音乐位置。玩家在任意小节第一拍拍手后启动预备，该次拍手不计分，等待一小节后正式判一个小节；等待启动时没有下落条，启动后只显示正式小节短线。`lead_in_bars` 可切回立即开始以比较体验。键盘事件对应最近目标，不再按第几次输入顺序匹配。支持暂停／继续、清空本轮、重来、配置重载和本机日志。

画面按最新要求使用 Arcade、上方五线谱与下落短线；不实现持续接触或长按音符。当前谱面为可配置的整小节循环练习模板，后续需要音乐组提供正式目标序列。手套、正式音效、Pass 条件、美术、TouchDesigner 同屏及现场联调仍待完成。验证条件与结果见[第 1 阶段软件验证](phase1-validation.md)。

## 建议功能分工

这是逻辑职责划分，不要求现在创建对应目录或空工程。

| 职责 | 需要处理的内容 |
| --- | --- |
| 内容与节奏数据 | 伴奏、拍掌采样、速度／拍号、小节主拍、目标落点、段落和版本一致性 |
| 播放与时间轴 | 播放位置、实际输出时间映射、播放批次、主拍入口；统一开始、暂停、停止和重置 |
| 输入适配与接触识别 | 模拟量采集、原始信号观察、阈值／滞回、去抖、接触／松开、事件时间与来源 |
| 校准与判定 | 时钟映射、延迟补偿、最近目标、容差、目标状态与判定结果 |
| 即时音效 | 预加载、持续音频流、有效拍掌及时触发；画面卡顿不得阻塞发声 |
| UI 与画面输出 | 草图布局、随时间轴运动的音符、判定线、即时反馈及通过效果；与音乐可视化配合 |
| 演出操作与记录 | 状态显示、必要控制、设备异常提示、恢复入口、校准与判定日志 |

建议音乐播放与拍掌音效共用同一音频引擎；输入事件分别供音效、判定和画面消费。音效不能等待画面刷新，音乐时钟也不能由拍掌事件或画面帧数推进。若最终由 DAW 主持播放，则需要验证宿主时间与输入／显示的对应关系，仍须满足集成操作要求。

## 分阶段开发与完成条件

| 阶段 | 工作与交付 | 完成条件 |
| --- | --- | --- |
| 0：明确首版边界 | 软件版选定 Python＋Arcade＋sounddevice；伴奏已提供，固定 90 BPM、4 秒首拍。手套路径暂缓，正式谱面和演出参数仍待确认 | 用可配置练习模板与生成音效先验证软件链路；现场硬件与正式参数不能由默认值替代 |
| 1：音乐与软件输入贯通（已完成） | 集成音乐播放与统一时间轴；任意小节第一拍拍手启动，预备一小节后正式打一小节；用带采集时间戳的软件输入接通“输入→音效→判定→画面” | 四分／八分混合落点；同一偏移不积累；启动拍手不计分；拍手前无短线，预备后只判正式小节；已知早晚输入结果可重现 |
| 2：接入手套并校准 | 采集真实模拟量，先观察接触波形再定阈值和去抖；接入同一事件接口；测量并记录输入、音效和返听链路，保存校准配置 | 单拍、持续合掌、快速连拍、松开重触发和断连恢复表现有记录；测得延迟分布，按演员反馈调整。模拟输入成功不替代此项 |
| 3：完成 UI 与结算 | 按最新要求完善五线谱、短线目标、判定线和反馈；确认进度与 Pass 条件后接入结算 | 短线到线时刻与目标时间一致；画面掉帧不改变音乐目标；通过与失败反馈符合已确认规则 |
| 4：同屏与演出联调 | 在预期 TouchDesigner 负载下做音乐可视化同屏；完善必要的开始／停止／重置和异常恢复；测试全曲与多次进入 | 音乐、输入、音效与画面在实际输出环境下稳定；旧轮次事件不影响新轮次；操作与恢复步骤经排练确认 |

每一阶段都保留可运行成果。UI 静态排版可以在阶段 1 后并行推进；最终动画应接真实音乐时间轴。阶段 2 的实物问题优先解决，避免完成美术后才发现输入或发声链路不可用。

## 首轮软件验证清单

以下为验证范围。第 1 阶段的确定时间输入与软件测试已完成，结果见[验证记录](phase1-validation.md)；涉及持续合掌、快速连拍和实际发声的项目仍等待手套及现场设备。验证应使用明确的测试音乐、目标表和校准参数，记录输入时间、校准时间、匹配目标、误差和状态。

- **节奏落点**：四分音符、两个八分音符及其混合；持续早拍／晚拍不能使后续目标漂移。
- **曲中进入**：至少两个不同小节的第一拍拍手启动；首次拍掌不计分，预备一小节后进入；只结算正式的一个小节；拍掌前不出现下落条。
- **最近匹配**：目标左右两侧、两个目标中点、窗口内外及恰好边界；重复命中和窗口重叠按已确认策略处理。
- **无输入与额外输入**：漏拍、多拍、持续合掌及快速连拍；具体结算期望在规则确认后补齐。
- **延迟校准**：注入已知固定偏移，验证补偿方向与单位；改变画面刷新速度，不应改变同一事件的匹配结果。
- **生命周期**：停止、暂停／继续、重置和曲中定位后，清理或隔离旧事件；暂停和跳段的目标保留策略依演出确认。

不以键盘手动拍出的“感觉正确”替代确定时间输入的逻辑验证。也不把软件日志时间当成接触到出声的实物测量。

## 实物与演出验证记录

建议用统一时基的示波器或同步采集设备测接触参考与音频输出，再用演员耳位麦克风测实际返听。记录手套／控制器、连接方式、电脑与系统、音频设备及驱动、采样率与缓冲、输入阈值与去抖、音效起音、返听距离、视觉负载、测量方法与试次数。分别报告接触到模拟音频输出、接触到演员耳位声音的延迟分布和重复／漏报情况。

低延迟是已确认需求，具体毫秒验收值尚未确认。先完成可测量的链路，再由演出团队确定可接受的容差、延迟与稳定性要求。

## 第 1 阶段之后

先在本机用键盘验证音乐与五线谱的对应，人工调整 `beat_offset_ms` 校准全曲起点，再替换为正式节奏谱面。手套到位后接入独立输入适配器，测量接触与松开、去抖、输入与返听链路，随后再推进完整结算、同屏联调与演出操作。

当前软件技术栈已确定，不为尚未接入的硬件和后续模块安装依赖或创建空框架。软件测试与音频设备估计值不能证明真实拍掌到耳朵的延迟；演出设备、正式谱面和玩法边界确认后，再确定现场验收与排练日程。

## 游戏内设置与首拍校准补充

按新增要求完成设置页：手动调整整曲偏移、输入补偿、容差、缓冲与两路音量；通过听音乐、按四分音符跟拍来估计首拍相位。至少 8 个稳定样本，稳定满 16 拍结束，最多采集 32 拍；校准结果预览后可加入设置并保存。新设置先验证、打开设备成功，再原子保存；失败保留原文件与原设置。

该流程估计当前首拍附近的相位，整拍／小节错位需人工粗调。人的跟拍偏差与真实输入／返听链路仍需排练和设备测量区分；不会自动修改 BPM。设置与校准软件验证见[验证记录](phase1-validation.md)。
