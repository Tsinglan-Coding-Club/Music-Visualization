# 拍掌节奏游戏开发计划

更新日期：2026 年 10 月 16 日。范围：集成音乐播放、手套拍掌输入、时间校准、节奏判定、低延迟音效和草图 UI，并保留与 TouchDesigner 音乐可视化同屏的路径。本次交付为规则记录与开发规划，尚未开始完整应用开发或执行硬件测试。

规则依据：[拍掌节奏游戏规则与画面参考](rhythm-game-rules.md)。下文是建议顺序，技术栈与参数均不因本计划而自动确定。

## 现有代码与差距

当前根目录 `beatgame.py` 已同步现有 GitHub 仓库的判定实验（上游提交 `5be3250`）：使用输入线程和队列收取回车输入，在输入线程记录 `perf_counter()` 时间戳，以首个输入为固定起点，累计 `[4, 8, 8, 4]` 的时值，依次比较后续输入。示例速度为 60 BPM，容差为一拍的八分之一，队列改为带超时等待。

这版已修正旧实验逐次更新起点、出队后才计时以及非阻塞轮询的问题。剩余差距是：首个输入仍是自由计时起点，没有音乐播放时钟；目标按输入序号顺序比较，尚不支持最近目标搜索、漏拍后继续正确匹配或任意小节主拍进入；音乐、手套采集、时间校准、音效和 UI 也尚未集成。不能把实验参数视为正式规则。本次同步保留上游代码，正式开发再确定是否沿用 Python。

## 建议功能分工

这是逻辑职责划分，不要求现在创建对应目录或空工程。

| 职责 | 需要处理的内容 |
| --- | --- |
| 内容与节奏数据 | 伴奏、拍掌采样、速度／拍号、小节主拍、目标落点、段落和版本一致性 |
| 播放与时间轴 | 播放位置、实际输出时间映射、播放批次、主拍入口；统一开始、暂停、停止和重置 |
| 输入适配与接触识别 | 模拟量采集、原始信号观察、阈值／滞回、去抖、接触／松开、事件时间与来源 |
| 校准与判定 | 时钟映射、延迟补偿、最近目标、容差、目标状态与判定结果 |
| 即时音效 | 预加载、持续音频流、有效拍掌及时触发；画面卡顿不得阻塞发声 |
| UI 与画面输出 | 草图布局、随时间轴运动的音符、判定线、即时反馈及通过效果；与音乐可视化配合 |
| 演出操作与记录 | 状态显示、必要控制、设备异常提示、恢复入口、校准与判定日志 |

建议音乐播放与拍掌音效共用同一音频引擎；输入事件分别供音效、判定和画面消费。音效不能等待画面刷新，音乐时钟也不能由拍掌事件或画面帧数推进。若最终由 DAW 主持播放，则需要验证宿主时间与输入／显示的对应关系，仍须满足集成操作要求。

## 分阶段开发与完成条件

| 阶段 | 工作与交付 | 完成条件 |
| --- | --- | --- |
| 0：明确首版边界 | 确认运行电脑、手套采集路径、首段音乐和入口语义；准备伴奏、目标落点、小节主拍与拍掌采样；选择能验证低延迟播放的技术栈 | 一段音乐及目标可对齐；主拍入口、目标生成方式和首版容差有明确约定。未定硬件时可先做软件实验，但不得据此宣称实物可用 |
| 1：音乐与软件输入贯通 | 集成音乐播放；建立统一时间轴；支持选择任意小节的主拍作为本轮起点；用带采集时间戳的软件输入接通“输入→音效→判定→临时画面” | 固定测试片段包含四分／八分混合落点；同一偏移不积累到下一拍；曲中入口正确；已知早晚输入能重现预期结果 |
| 2：接入手套并校准 | 采集真实模拟量，先观察接触波形再定阈值和去抖；接入同一事件接口；测量并记录输入、音效和返听链路，保存校准配置 | 单拍、持续合掌、快速连拍、松开重触发和断连恢复表现有记录；测得延迟分布，按演员反馈调整。模拟输入成功不替代此项 |
| 3：完成草图 UI 与结算 | 按草图实现规则区、顶部节奏与速度、音符块、判定线和反馈；确认图中标记语义后接入进度与 Pass；补漏拍、多拍等规则 | 音符到线时刻与目标时间一致；画面掉帧不改变判定；通过与失败反馈符合已确认规则 |
| 4：同屏与演出联调 | 在预期 TouchDesigner 负载下做音乐可视化同屏；完善必要的开始／停止／重置和异常恢复；测试全曲与多次进入 | 音乐、输入、音效与画面在实际输出环境下稳定；旧轮次事件不影响新轮次；操作与恢复步骤经排练确认 |

每一阶段都保留可运行成果。UI 静态排版可以在阶段 1 后并行推进；最终动画应接真实音乐时间轴。阶段 2 的实物问题优先解决，避免完成美术后才发现输入或发声链路不可用。

## 首轮软件验证清单

以下为待执行的验证，不是测试结果。使用明确的测试音乐、目标表和校准参数，记录输入时间、校准时间、匹配目标、误差和状态。

- **节奏落点**：四分音符、两个八分音符及其混合；持续早拍／晚拍不能使后续目标漂移。
- **曲中进入**：至少两个不同小节的主拍进入；播放启用与一轮结算分开处理；不结算进入前的目标。
- **最近匹配**：目标左右两侧、两个目标中点、窗口内外及恰好边界；重复命中和窗口重叠按已确认策略处理。
- **无输入与额外输入**：漏拍、多拍、持续合掌及快速连拍；具体结算期望在规则确认后补齐。
- **延迟校准**：注入已知固定偏移，验证补偿方向与单位；改变画面刷新速度，不应改变同一事件的匹配结果。
- **生命周期**：停止、暂停／继续、重置和曲中定位后，清理或隔离旧事件；暂停和跳段的目标保留策略依演出确认。

不以键盘手动拍出的“感觉正确”替代确定时间输入的逻辑验证。也不把软件日志时间当成接触到出声的实物测量。

## 实物与演出验证记录

建议用统一时基的示波器或同步采集设备测接触参考与音频输出，再用演员耳位麦克风测实际返听。记录手套／控制器、连接方式、电脑与系统、音频设备及驱动、采样率与缓冲、输入阈值与去抖、音效起音、返听距离、视觉负载、测量方法与试次数。分别报告接触到模拟音频输出、接触到演员耳位声音的延迟分布和重复／漏报情况。

低延迟是已确认需求，具体毫秒验收值尚未确认。先完成可测量的链路，再由演出团队确定可接受的容差、延迟与稳定性要求。

## 下一次开发的起点

优先取得一段实际音乐、对应节奏和一条拍掌采样，并确认演出电脑及采集设备。首个开发成果聚焦“音乐播放＋主拍进入＋四分／八分目标＋软件拍掌输入＋即时音效＋简易判定显示”；随后用真实手套替换软件输入，完成校准，再推进完整 UI 和同屏联调。

在这些条件未齐时，可以用明确标为测试用的音频／目标做软件验证，但不默认选定生产技术栈、不安装未确定模块的依赖，也不对未测硬件承诺效果。当前不估算具体工期；素材、设备、玩法边界确定后再排开发与联排日程。
